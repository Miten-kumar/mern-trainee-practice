# Performance results

Generated by running `npm run perf` (`backend/scripts/perf-test.js`) against
the seeded data — 12 posts, 6 users, ~28 comments — with the backend running
locally. The script hits the same "posts feed with author + comments" data
three different ways and reports HTTP requests, simulated DB queries, and
wall-clock time.

```
Comparing against http://localhost:4000 — fetching all posts + author + comments

Approach                               HTTP requests    DB queries   Time (ms)
--------------------------------------------------------------------------------
REST (naive, N+1)                      25               25           294
REST (optimized /feed)                 1                25           27
GraphQL (single query + DataLoader)    1                3            55
```

## Reading these numbers

- **REST naive** makes one request for the post list, then two more per post
  (author + comments) — `1 + 12*2 = 25` requests, each one a real HTTP round
  trip. This is the N+1 problem as most people first meet it.
- **REST optimized** is a single request, but under the hood the hand-built
  `/api/posts/feed` route still loops over every post and queries the author
  and comment count individually — 25 DB queries, just moved server-side and
  hidden from the client. It's fast here only because the simulated network
  hop between "client" and "server" happens once instead of 25 times; the
  database work didn't actually shrink.
- **GraphQL** makes one request and, thanks to DataLoader batching
  (`userLoader`, `commentsByPostLoader`), turns "12 author lookups + 12
  comment lookups" into **one batched call for each** — `posts.findAll` +
  `users.findByIds` + `comments.findByPostIds` = 3 total queries.

The DB query column is the fairest comparison between the optimized REST
endpoint and GraphQL, since both are down to 1 HTTP request. That's where
DataLoader's batching shows up: 25 queries vs 3, for identical output data.

## Why GraphQL's time (55ms) isn't the fastest

REST optimized (27ms) still edges out GraphQL (55ms) in this run, even with
fewer DB queries. Two reasons, both artifacts of comparing against a
simulated in-memory "database" rather than a real one:

1. GraphQL's execution engine and DataLoader's batch scheduling add a small
   amount of overhead per request that a plain Express route doesn't have.
2. The 25 "queries" behind REST's `/feed` endpoint run concurrently
   (`Promise.all`), while DataLoader intentionally waits a tick to collect
   everything into a batch before firing — that tiny wait is worth it when
   each query is a real network hop to a database, but shows up as pure
   overhead against a near-instant in-memory store.

Against a real database under real network latency (where each query is
milliseconds, not microseconds), the gap would flip hard in GraphQL's
favor — that's the whole reason DataLoader batching exists. This project
optimizes for making the *query count* difference undeniable, not for
producing a flattering millisecond number.

## Re-running this yourself

```bash
cd backend
npm install
npm start          # terminal 1
npm run perf        # terminal 2
```

Numbers will vary a little between runs (event loop scheduling, machine
load) — the request-count and DB-query-count columns are the ones that
matter, since they don't depend on timing.
